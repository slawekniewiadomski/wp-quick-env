# AGENTS.md — wp-quick-env

Reference for AI agents working with this WordPress Docker development environment.

---

## Project Overview

**wp-quick-env** — A minimal, configurable WordPress dev stack using Docker Compose + Task.

- **Stack**: WordPress (Apache), MariaDB, phpMyAdmin, wp-cli, Composer, Node.js
- **Config**: Single `.env` file controls all versions, ports, credentials
- **Theme/Plugin dirs**: `wp-content/themes` and `wp-content/plugins` start empty (gitignored). Bundled themes copied from image on first boot.
- **Target**: Local development only — never expose to internet.

## Quick Commands Reference

| Command | Purpose |
|---------|---------|
| `task init` | Interactive `.env` generator (versions, ports, credentials) |
| `task init --yes` | Non-interactive, accepts all defaults |
| `task init --force` | Regenerate `.env` without prompts |
| `task start` | Build + start containers (`docker compose up -d --build`) |
| `task stop` | Stop containers |
| `task restart` | Rebuild + restart (required after version changes) |
| `task install` | Run `wp core install` from `.env` (idempotent) |
| `task wp -- <args>` | Run wp-cli, e.g. `task wp -- plugin list` |
| `task theme:clone -- <git-url> [name]` | Clone theme into `wp-content/themes/`, sets `THEME_DIR` |
| `task seed` | Restore bundled WP themes if `wp-content/themes` was emptied |
| `task ports` | Show current port mappings |
| `task ports:new` | Allocate new random port block |
| `task db:export` | Export database to `db/` |
| `task db:import FILE=dump.sql` | Import database dump |
| `task db:shell` | Open MySQL shell |
| `task composer:install` / `task composer:update` | Composer in `THEME_DIR` |
| `task node:install` / `task node:dev` / `task node:build` | npm in `THEME_DIR` |
| `task check` | Validate image tags and port availability |
| `task versions` | Print resolved version matrix |
| `task ps` / `task logs` / `task shell` | Inspect containers |
| `task clear-cache` / `task fix-perms` / `task reset` | Maintenance |

## Environment Setup (`.env`)

**Never commit `.env`**. Use `.env.example` as reference.

### Key Variables

| Variable | Description | Example |
|----------|-------------|---------|
| `COMPOSE_PROJECT_NAME` | Unique stack name (containers, volumes, ports) | `my-site` |
| `WP_VERSION` | WordPress version | `6.9` |
| `PHP_VERSION` | PHP version (see Safe PHP Versions below) | `8.4` |
| `PHP_SOURCE` | `official` (PHP ≥8.3) or `sury` (PHP <8.3) | `official` |
| `NODE_VERSION` | Node.js version | `22` |
| `WP_CLI_VERSION` | Pinned wp-cli phar version | `2.11.0` |
| `COMPOSER_VERSION` | Composer version | `2.8` |
| `MARIADB_VERSION` | MariaDB image tag | `11.4` |
| `PHPMYADMIN_VERSION` | phpMyAdmin image tag | `5.2` |
| `WP_PORT` | WordPress port (host) | `20000` |
| `PMA_PORT` | phpMyAdmin port (host) | `20001` |
| `VITE_PORT` | Vite HMR port (host) | `20010` |
| `DB_NAME` / `DB_USER` / `DB_PASSWORD` / `DB_ROOT_PASSWORD` | Database credentials |
| `WP_ADMIN_USER` / `WP_ADMIN_PASSWORD` / `WP_ADMIN_EMAIL` | WordPress admin |
| `THEME_DIR` | Theme path for Node/Composer tasks | `wp-content/themes/my-theme` |
| `WP_DEBUG_LOG_FILE` | Per-stack WordPress debug log (relative to `wp-content/`) | `wp-content/debug.log` |
| `HOST_UID` / `HOST_GID` | Host user/group for file permissions | `1000` / `1000` |

### Safe PHP Versions

Only actively patched PHP branches are allowed:

| PHP Version | Source | Base Image |
|-------------|--------|------------|
| 8.3, 8.4, 8.5 | Official | `wordpress:<WP_VERSION>-php<PHP_VERSION>-apache` |
| 5.6, 7.0–7.4, 8.0–8.2 | Ondřej Surý | Debian bookworm + packages.sury.org |

- `PHP_SOURCE` is derived from `PHP_VERSION` by `task init`
- `task check` refuses mismatches or unsupported branches
- **Below PHP 7.2**: `COMPOSER_VERSION` defaults to `2.2` (Composer 2.3+ requires PHP 7.2.5+)
- **WP/PHP compatibility**: `task check` warns if `WP_VERSION` doesn't support `PHP_VERSION`

### Ports

- Default block: `20000–29999` (below Linux ephemeral range `32768–60999`)
- Offsets: `WP_PORT` = base, `PMA_PORT` = base+1, `VITE_PORT` = base+10
- Verified free (host listeners + Docker-published) before writing to `.env`
- `WP_HOME` / `WP_SITEURL` derived from `WP_PORT` in `compose.yml` — URL always matches mapping

## Common Workflows

### New Project from Template

```bash
gh repo clone <you>/wp-quick-env my-new-site -- --depth 1
cd my-new-site
task init
task start && task install
```

- `task init` proposes directory name as `COMPOSE_PROJECT_NAME`
- Multiple clones run simultaneously (independent containers, volumes, ports)

### Add Your Theme

```bash
task theme:clone -- https://github.com/your/theme my-theme
```

- Clones into `wp-content/themes/my-theme`
- Sets `THEME_DIR=wp-content/themes/my-theme` in `.env`
- Enables `task node:*` and `task composer:*` commands

### Multi-PHP Debug Compare (opt-in)

Run the same theme on two PHP versions at once to find upgrade regressions:

```bash
task init --multi-php 7.4,8.0      # .env (baseline) + .env.php74 + .env.php80
task start:all
task install:php74 && task install:php80
task debug:compare
```

How it works:

- Each `.env.phpXX` has a distinct `COMPOSE_PROJECT_NAME` (`<project>-php74`), its own port block (`20xxx` / `21xxx` by default, `--base` shifts both), its own database volume, and its own `WP_DEBUG_LOG_FILE=wp-content/debug.log.phpXX`.
- `compose.yml` is unchanged; both stacks use the same service names but different compose projects.
- `wp-content/` is shared, so both stacks serve the same theme and plugins.
- `bin/env-run <env-file> <cmd>` loads an env file literally (no shell expansion) and exports it, overriding the default `.env` that Task loads. Multi tasks use it.
- Debug constants are always on in `compose.yml`: `WP_DEBUG`, `WP_DEBUG_LOG`, `WP_DEBUG_DISPLAY`, `SCRIPT_DEBUG`.
- `task debug:compare` discovers URLs via wp-cli (posts, pages, categories, tags, authors, `/`, `/search/`, `/feed/`), crawls both stacks with Playwright, truncates the per-stack debug log before each page, and reports URLs where the newer PHP adds PHP errors, JS console errors, or changes HTTP status.
- Crawler prerequisite: `pip install playwright && playwright install chromium`.
- Opt-in: without `--multi-php`, nothing changes and single-stack tasks behave exactly as before.

### Run wp-cli on a specific multi-PHP stack

```bash
task wp:php74 -- plugin list
task wp:php80 -- core version
# or directly:
ENV_FILE=.env.php74 ./bin/wp plugin list
```

### Run wp-cli Commands

```bash
task wp -- plugin list
task wp -- core version
task wp -- search-replace 'http://localhost:20000' 'http://localhost:20500' --all-tables
```

- Runs as `www-data` inside the WordPress container

### Database Operations

```bash
task db:export                    # Dumps to db/dump-<timestamp>.sql
task db:import FILE=db/dump.sql   # Imports specified file
task db:shell                     # Opens mysql shell
```

### Debug / Inspect Containers

```bash
task ps              # List containers
task logs            # Follow all logs
task logs wordpress  # Follow single service
task shell           # Bash in wordpress container as www-data
task shell root      # Bash as root
```

### Change PHP Version

```bash
# Edit .env
PHP_VERSION=8.2
PHP_SOURCE=sury
# Then rebuild
task restart
```

- `task check` validates the combination
- Crossing PHP 8.3 boundary requires `PHP_SOURCE` change

## Key Conventions

1. **Composer runs on the WordPress PHP** — `wordpress` and `composer` services use the **same built image**. Composer validates against the exact PHP binary/extensions serving the site.

2. **Port block stability** — Once written to `.env`, ports stay fixed across restarts. Use `task ports:new` to re-roll.

3. **`localhost` not `127.0.0.1`** — HMR, cookies, asset URLs all assume `localhost`.

4. **Node runs as host UID** — `HOME` and npm cache point to `/tmp` inside container.

5. **Rebuild on version changes** — Any version change in `.env` requires `task restart` (runs `--build`).

## Gotchas for Agents

- **Empty dirs are intentional** — `wp-content/themes` and `wp-content/plugins` are gitignored and start empty. Bundled themes (Twenty Twenty-Five, etc.) are copied from the image on first boot by WordPress's entrypoint. `task seed` only needed if you manually emptied the directory.

- **Composer behind `tools` profile** — `docker compose up` does NOT start the composer service. Use `task composer:*` (runs on demand) or `docker compose run --rm composer ...`.

- **PHP <8.3 uses Surý builds** — Image name ends in `-sury`, rebuild downloads packages instead of pulling official tag.

- **Changing ports after install** — Login/redirects work (config wins over DB), but absolute URLs in post content still point to old port. Fix with:
  ```bash
  task wp -- search-replace 'http://localhost:<old>' 'http://localhost:<new>' --all-tables
  ```

- **Root-owned files** — Should not happen (image remaps `www-data`; node/composer run as your UID). If they appear after manual `docker compose exec` as root, run `task fix-perms`.

- **`task reset` deletes the database volume** — Always `task db:export` first.

- **No `.env` = no start** — `task start` fails if `.env` missing. Run `task init` first.

- **Multi-PHP env files** — `.env.php74` / `.env.php80` are gitignored (`.env.php*`). Never edit `compose.yml` for multi mode; each stack is just a different compose project via its env file. Use `bin/env-run` or the generated `task *:phpXX` tasks so the right file wins over `.env`.

- **Debug display is on** — `compose.yml` sets `WP_DEBUG_DISPLAY`, `WP_DEBUG_LOG`, `SCRIPT_DEBUG` and `WP_DEBUG` true so errors are visible. `WP_DEBUG_LOG_FILE` picks the per-stack log; do not point two stacks at the same file.

- **Crawler needs Playwright** — `task debug:compare` exits with instructions if `playwright` / Chromium is missing. Installed on the host, not in a container.

## Security Note

**Development only.** Database credentials in `.env` are intentionally weak, MySQL root is reused by phpMyAdmin, and debug output is on. Never expose this stack to the internet.
